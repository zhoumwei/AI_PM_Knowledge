#### 核心指标

| 指标名称 | 指标定义 | 计算公式 | 数据来源 |
|----------|----------|----------|----------|
| 推荐点击率（CTR） | 用户点击推荐内容的比例 | 点击次数 / 曝光次数 | 行为日志 |

|----------|----------|----------|----------|

### 2.4 样本量计算表

| 参数 | 值 | 说明 |
|------|-----|------|
| 对照组基准转化率（p₁） | 8% | 根据历史数据 |
| 实验组预期转化率（p₂） | 9% | 预期提升后的值 |
| 最小可检测效果（MDE） | 1% | p₂ - p₁ |
| 相对提升 | 12.5% | (p₂ - p₁) / p₁ |
| 置信水平（α） | 95% | 常用值 |
| 统计功效（β） | 80% | 常用值 |
| Z值 | 1.96 | 95%置信度对应 |
| 每组样本量 | 10,000 | 计算结果 |

**样本量计算公式**：
```
n = (Z² × (p₁(1-p₁) + p₂(1-p₂))) / (p₂ - p₁)²
```

**在线计算工具**：
- [Evan Miller's Sample Size Calculator](https://www.evanmiller.org/ab-testing/sample-size.html)
- [Google Optimize Sample Size Calculator](https://support.google.com/optimize/answer/6281787)

### 2.5 分组设计表

| 分组名称 | 流量占比 | 用户特征 | 版本描述 |
|----------|----------|----------|----------|
| 对照组（A组） | 50% | 随机分配 | 当前推荐算法v1.0 |
| 实验组（B组） | 50% | 随机分配 | 新推荐算法v2.0 |

**分组原则**：
- 随机分配：使用用户ID哈希取模或随机数生成
- 样本量相等：两组流量分配比例一致
- 同期测试：同一时间段进行
- 隔离性：避免其他实验干扰

### 2.6 用户分组方法

#### 方法一：用户ID哈希取模

**原理**：将用户ID通过哈希函数转换为数值，再取模分配到不同分组。

**优点**：
- 用户分组稳定，同一用户始终在同一组
- 易于实现和验证
- 支持用户分桶（互斥实验）
- 可预测性强，便于调试

**缺点**：
- 哈希函数选择不当可能导致分布不均
- 需要提前规划分桶策略

**实现示例**：

```python
def hash_group(user_id, bucket_count=100):
    import hashlib
    hash_value = int(hashlib.md5(str(user_id).encode()).hexdigest(), 16)
    return hash_value % bucket_count

def assign_group(user_id):
    bucket = hash_group(user_id)
    if bucket < 50:
        return 'control'
    else:
        return 'treatment'
```

**分桶策略**：

| 分桶数 | 用途 |
|--------|------|
| 100桶 | 标准分桶，支持1%精度的流量控制 |
| 1000桶 | 精细分桶，支持0.1%精度的流量控制 |
| 互斥分桶 | 多个实验使用不同的分桶，避免用户同时参与多个实验 |

#### 方法二：随机数生成

**原理**：为每个用户生成随机数，根据随机数分配分组。

**优点**：
- 简单直接，实现成本低
- 随机性好，分布均匀

**缺点**：
- 用户刷新页面可能重新分配（需持久化存储）
- 不可预测，难以调试

**实现示例**：

```python
import random

def assign_group_random(user_id):
    random.seed(hash(user_id))
    if random.random() < 0.5:
        return 'control'
    else:
        return 'treatment'
```

#### 方法三：Cookie/本地存储

**原理**：首次访问时分配分组，将分组信息存储在Cookie或本地存储中。

**优点**：
- 用户体验稳定
- 前端可直接实现，无需服务端参与
- 分组结果即时生效

**缺点**：
- 用户清除Cookie会重新分配
- 需要服务端验证防止作弊
- 跨设备分组不一致

**实现示例（前端）**：

```javascript
function getExperimentGroup() {
    let group = localStorage.getItem('ab_test_group');
    if (!group) {
        group = Math.random() < 0.5 ? 'control' : 'treatment';
        localStorage.setItem('ab_test_group', group);
    }
    return group;
}
```

#### 方法四：服务端持久化存储

**原理**：首次分配分组后，将结果存储在数据库中，后续请求从数据库读取。

**优点**：
- 分组结果持久可靠
- 支持跨设备一致性
- 便于数据追踪和审计

**缺点**：
- 需要数据库读写，增加服务端开销
- 首次请求延迟增加

**实现示例（数据库表结构）**：

```sql
CREATE TABLE experiment_groups (
    user_id VARCHAR(64) PRIMARY KEY,
    experiment_id VARCHAR(32),
    group_type VARCHAR(16),
    assigned_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

#### 分组方法对比

| 方法 | 稳定性 | 实现复杂度 | 跨设备一致性 | 适用场景 |
|------|--------|------------|--------------|----------|
| 用户ID哈希取模 | 高 | 低 | 高 | 标准A/B测试 |
| 随机数生成 | 中（需持久化） | 低 | 中 | 简单实验 |
| Cookie/本地存储 | 中 | 低 | 低 | 前端实验、短期实验 |
| 服务端持久化存储 | 高 | 中 | 高 | 重要实验、长期实验 |

#### 4.1.3 数据跟踪方法

##### 方法一：埋点跟踪

**原理**：在关键页面和事件中嵌入埋点代码，记录用户行为。

**埋点类型**：

| 类型 | 说明 | 示例 |
|------|------|------|
| 页面埋点 | 记录页面访问 | 首页访问、详情页访问 |
| 点击埋点 | 记录按钮/链接点击 | 购买按钮、提交按钮 |
| 曝光埋点 | 记录内容曝光 | 推荐内容曝光 |
| 转化埋点 | 记录目标完成 | 订单完成、注册成功 |

**优点**：
- 灵活性高，可自定义跟踪任何事件
- 数据粒度细，支持详细分析
- 实时性好，数据即时上报

**缺点**：
- 开发成本高，需要逐个埋点
- 维护成本高，页面变更需同步更新埋点
- 可能遗漏关键事件

**实现示例**：

```javascript
function trackPageView(pageName) {
    sendToAnalytics({
        event: 'page_view',
        page: pageName,
        group: getExperimentGroup(),
        timestamp: Date.now(),
        user_id: getUserID()
    });
}

function trackClick(elementName) {
    sendToAnalytics({
        event: 'click',
        element: elementName,
        group: getExperimentGroup(),
        timestamp: Date.now(),
        user_id: getUserID()
    });
}
```

##### 方法三：数据仓库聚合

**原理**：将埋点数据和日志数据汇总到数据仓库，按分组聚合分析。

**数据处理流程**：

```
埋点数据 → 实时流处理 → 数据仓库 → 分析报表
日志数据 → 批处理     →         →
```

**优点**：
- 数据集中管理，便于统一分析
- 支持复杂查询和多维分析
- 数据可复用，支持多种分析场景

**缺点**：
- 建设成本高，需要数据仓库基础设施
- 数据延迟，不支持实时分析
- 需要专业的数据团队维护

**SQL查询示例**：

```sql
SELECT
    group_type,
    COUNT(DISTINCT user_id) AS user_count,

    SUM(click_count) / SUM(impression_count) AS ctr
```

### 4.2 统计分析

#### 步骤一：数据汇总

```sql
-- 计算各组CTR
SELECT
    group_type,
    COUNT(DISTINCT user_id) AS user_count,
    SUM(impression_count) AS total_impressions,
    SUM(click_count) AS total_clicks,
    SUM(click_count) / SUM(impression_count) AS ctr
FROM experiment_data
WHERE experiment_id = 'AB-2024-001'
GROUP BY group_type;
```

#### 步骤二：统计检验

| 检验方法 | 适用场景 | 执行工具 |
|----------|----------|----------|
| 卡方检验 | 分类数据（CTR、转化率） | Python scipy、Excel |
| t检验 | 连续数据（停留时长） | Python scipy、Excel |
| 双样本比例检验 | 两组比例对比 | Python statsmodels |

**Python代码示例**：

```python
from statsmodels.stats.proportion import proportions_ztest

# 实验组：n1=10000, clicks1=900
# 对照组：n2=10000, clicks2=800

count = [900, 800]
nobs = [10000, 10000]

stat, p_value = proportions_ztest(count, nobs, alternative='two-sided')

print(f"Z统计量: {stat:.2f}")
print(f"p值: {p_value:.4f}")
```

#### 步骤三：效果计算

|------|----------|------|
| 绝对提升 | 实验组指标 - 对照组指标 | 9% - 8% = +1% |
| 相对提升 | (实验组 - 对照组) / 对照组 × 100% | (9% - 8%) / 8% = +12.5% |
| 置信区间 | 效果估计值 ± 边际误差 | +1% ± 0.3% |

## 六、实战案例：推荐算法A/B测试

### 6.1 实验背景

**问题**：首页推荐算法v1.0上线半年后，CTR从10%下降至8%，低于行业平均水平10%。

**目标**：验证新推荐算法v2.0能否提升CTR至9%以上。

### 6.2 实验设计

**实验方案**：

| 字段 | 内容 |
|------|------|
| 实验名称 | 推荐算法v2.0效果验证 |
| 实验ID | AB-2024-001 |
| 实验负责人 | 张三 |
| 业务背景 | 推荐CTR下降，需要验证新算法效果 |
| 实验目标 | CTR提升12.5%（8%→9%） |
| 实验周期 | 2024-01-15 ~ 2024-01-29（14天） |
| 流量分配 | 对照组50%，实验组50% |
| 预计样本量 | 每组10,000用户 |

**假设设计**：
> 如果我们将推荐算法从v1.0升级到v2.0，那么推荐点击率将提升12.5%以上，置信度95%。

**指标定义**：

| 指标类型 | 指标名称 | 定义 |
|----------|----------|------|
| 核心指标 | CTR | 点击次数/曝光次数 |
| 辅助指标 | 停留时长 | 页面停留时间 |
| 辅助指标 | 7日留存 | 7日后活跃用户比例 |

### 6.3 实验执行

**流量分配**：
- 对照组（A组）：50%流量，使用v1.0算法
- 实验组（B组）：50%流量，使用v2.0算法

**每日监控**：

| 日期 | 实验组CTR | 对照组CTR | 差异 | 显著性 | 样本量 |
|------|-----------|-----------|------|--------|--------|
| Day 1 | 8.2% | 8.0% | +0.2% | 不显著 | 1,200 |
| Day 3 | 8.5% | 8.1% | +0.4% | 不显著 | 3,500 |
| Day 7 | 8.8% | 8.0% | +0.8% | p=0.08 | 7,000 |
| Day 10 | 8.9% | 8.0% | +0.9% | p=0.04 | 8,500 |
| Day 14 | 9.0% | 8.0% | +1.0% | p=0.02 | 10,000 |

### 6.4 数据分析

**最终数据汇总**：

| 分组 | 用户数 | 曝光次数 | 点击次数 | CTR |
|------|--------|----------|----------|-----|
| 对照组 | 10,000 | 50,000 | 4,000 | 8.0% |
| 实验组 | 10,000 | 50,000 | 4,500 | 9.0% |

**统计检验**：
- Z统计量：4.47
- p值：0.0000（<0.05，差异显著）

**效果计算**：
- 绝对提升：+1.0%
- 相对提升：+12.5%
- 95%置信区间：+0.7% ~ +1.3%

**辅助指标分析**：
- 停留时长：实验组增加15%（显著）
- 7日留存：实验组增加8%（显著）

### 6.5 决策与上线

**决策**：全量上线新算法v2.0

**决策依据**：
1. CTR提升12.5%，p<0.05，差异显著
2. 辅助指标均正向提升
3. 无负面影响

**上线计划**：
- D+2：决策会议通过
- D+3~D+5：开发上线版本
- D+6：灰度发布（20%流量）
- D+7：全量上线

## 九、常见问题与解决方案

### 9.1 样本量不足

**问题**：实验结束但样本量未达到预期

**解决方案**：
- 延长实验周期
- 增加流量分配比例
- 降低最小可检测效果要求

### 9.2 数据污染

**问题**：数据受到其他实验或活动干扰

**解决方案**：
- 使用互斥实验设计
- 控制实验期间的其他变量
- 排除异常数据

### 9.3 多重比较问题

**问题**：测试多个指标导致假阳性率增加

**解决方案**：
- 聚焦核心指标（1-2个）
- 使用Bonferroni校正
- 控制检验次数

### 9.4 效果不显著

**问题**：实验结果差异不显著

**解决方案**：
- 检查样本量是否足够
- 检查数据质量
- 考虑是否需要调整实验设计
- 评估是否继续实验或放弃

### 9.5 辅助指标下降

**问题**：核心指标提升但辅助指标下降

**解决方案**：
- 分析下降原因
- 评估整体影响
- 权衡利弊后决策
- 考虑是否需要优化方案
