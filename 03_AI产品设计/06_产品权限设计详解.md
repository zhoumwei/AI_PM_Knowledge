# 产品权限设计详解

## 学习目标

学完本文档后，你将能够：

1. 理解权限设计的核心概念：身份认证、访问控制、授权、鉴权
2. 掌握主流权限模型：ACL、RBAC、ABAC、PBAC、ReBAC
3. 区分 B 端、C 端、SaaS 平台、开放平台等不同类型产品的权限设计异同
4. 设计权限矩阵、权限分组、角色层级、数据权限
5. 识别权限设计中的常见陷阱与安全风险
6. 与研发团队对齐权限系统的技术实现与落地

---

## 一、权限设计的基本概念

### 1.1 权限系统的两个核心动作

权限系统的本质是回答两个问题：

| 问题 | 动作 | 英文 | 通俗解释 |
|------|------|------|----------|
| 你是谁？ | 身份认证（Authentication，简称 AuthN） | Authentication | 登录、证明身份 |
| 你能做什么？ | 访问控制（Authorization，简称 AuthZ） | Authorization | 判断是否有权限做某件事 |

国内研发常把这两件事统称为"鉴权"，但严格意义上有区别：
- **认证（AuthN）**：确认用户身份（你是张三吗？）
- **授权（AuthZ）**：判断用户能否执行某个操作（张三能删除订单吗？）

### 1.2 权限的三个维度

一个完整的权限由三个维度共同决定：

```
权限 = 主体（Who） × 资源（What） × 操作（How）
```

| 维度 | 说明 | 举例 |
|------|------|------|
| **主体 Who** | 谁来操作 | 用户、用户组、角色、服务、应用 |
| **资源 What** | 操作的对象 | 页面、菜单、按钮、API、数据行、文件 |
| **操作 How** | 具体动作 | 查看、创建、编辑、删除、导出、审批 |

举例："张三（Who）可以对订单列表（What）执行导出（How）"就是一条权限规则。

### 1.3 功能权限 vs 数据权限

这是产品经理最容易混淆、也是最容易漏设计的部分：

| 维度 | 功能权限 | 数据权限 |
|------|----------|----------|
| 解决问题 | 能不能做这个操作 | 能对哪些数据做这个操作 |
| 判断对象 | 操作本身 | 操作背后的数据范围 |
| 举例 | 张三能"查看订单"吗 | 张三能查看"北京地区"的订单吗 |
| 典型实现 | 角色权限矩阵 | 组织架构过滤 / 行级权限 |
| 设计漏点 | 容易漏配按钮权限 | 多租户、跨部门数据隔离易忽略 |

**经典 Bug**：PM 给销售经理配了"查看所有订单"的功能权限，但忘了做数据权限，结果销售经理 A 能看到销售经理 B 的客户订单 → 数据越权。

## 二、主流权限模型

### 2.1 ACL（Access Control List）访问控制列表

**思路**：为每个资源维护一个"可访问主体列表"。

```
订单 #001: [张三: 查看, 李四: 查看+编辑]
订单 #002: [李四: 查看+编辑+删除]
```

**优点**：粒度细，控制精确。

**缺点**：主体多、资源多时列表爆炸；权限变更要遍历每个资源；不适合大型系统。

**适用**：文件系统（Linux 文件权限）、 Wiki 协作平台的页面共享。

### 2.2 RBAC（Role-Based Access Control）基于角色

**思路**：用户 → 角色 → 权限。用户不直接拥有权限，而是通过角色间接获得。

```
张三 → 销售经理（角色）→ [查看订单, 编辑客户, 导出报表]
李四 → 管理员（角色）→ [所有权限]
```

这是**企业级 B 端产品最主流的权限模型**。

**RBAC 三层标准**：

| 层级 | 名称 | 特点 |
|------|------|------|
| RBAC0 | 基础模型 | User-Role-Permission 三元组 |
| RBAC1 | 带角色继承 | 角色之间有上下级关系，子角色继承父角色权限 |
| RBAC2 | 带约束 | 增加互斥角色（如制单人和审批人不能同一人）、角色数量限制 |
| RBAC3 | 完整模型 | RBAC1 + RBAC2 |

**优点**：管理简单、可读性强、与组织架构天然契合、审计容易。

**缺点**：角色爆炸（一人多角色时角色数量失控）；细粒度控制弱（"销售经理能查看自己部门订单"这种数据权限难表达）。

### 2.3 ABAC（Attribute-Based Access Control）基于属性

**思路**：根据主体属性、资源属性、环境属性、操作属性动态计算权限。

```
允许 编辑订单 当:
  主体.部门 == 资源.创建部门
  AND 主体.职级 >= 资源.密级
  AND 环境.时间 在 工作时间
  AND 操作 != 删除
```

**优点**：极细粒度；可动态适应；能表达复杂业务规则。

**缺点**：实现复杂；规则难维护；可读性差；调试困难。

**适用**：金融、政企、医疗等对数据安全要求极高的场景；多租户 SaaS 的精细化数据隔离。

### 2.4 PBAC（Policy-Based Access Control）基于策略

**思路**：把权限规则抽象为"策略"，用 DSL 或规则引擎表达。

**与 ABAC 的区别**：PBAC 是 ABAC 的工程化包装，强调"策略即代码"。典型实现：AWS IAM、Open Policy Agent（OPA）。

### 2.5 ReBAC（Relationship-Based Access Control）基于关系

**思路**：权限由主体与资源之间的关系图决定。

```
张三 是 项目A 的 owner
项目A 包含 文件X
→ 张三 可 编辑 文件X
```

**典型实现**：Google Zanzibar（YouTube、Drive、Cloud 的权限底层）、AuthZed SpiceDB。

**适用**：社交关系型权限（好友可见、团队成员可编辑）、复杂资源继承关系（文件夹 → 文件 → 评论）。

### 2.6 模型选型决策表

| 场景特征 | 推荐模型 |
|----------|---------|
| 中小企业内部系统，角色清晰 | RBAC |
| 大型企业，角色多且有继承关系 | RBAC1/RBAC3 |
| 金融/医疗，需细粒度数据权限 | RBAC + ABAC 混合 |
| 社交/协作产品，权限由关系决定 | ReBAC |
| 开放平台 / API 网关 | PBAC（OPA） |
| 文件系统 / 简单资源 | ACL |

## 三、不同类型产品的权限设计异同

这是本文档的核心章节。B 端、C 端、SaaS、开放平台、AI 产品在权限设计上有共性也有显著差异。

### 3.1 共性基础（所有产品都需要）

1. **身份认证层**：注册 / 登录 / 找回密码 / 第三方登录 / SSO
2. **会话管理**：Token / Session / Refresh Token / 多端登录控制
3. **操作审计**：关键操作要留痕（谁、何时、做了什么）
4. **权限变更追溯**：谁能改权限、改了什么要有记录
5. **最小权限原则**：默认给最小权限，按需扩展

### 3.2 B 端企业产品（ERP/CRM/OA/HR）

| 维度 | 设计要点 |
|------|----------|
| **权限模型** | RBAC 为主，复杂场景 RBAC+ABAC 混合 |
| **用户来源** | 企业管理员创建 / 导入，非自助注册 |
| **角色定义** | 与组织架构对齐（部门、岗位、职级） |
| **角色继承** | 上级默认继承下级权限（部门经理见下属数据） |
| **数据权限** | 必须做，按部门 / 团队 / 项目过滤数据 |
| **互斥角色** | 制单与审批分离（SOX 审计要求） |
| **权限审批** | 角色变更通常需上级审批 |
| **典型示例** | 销售只能看自己客户；销售经理看团队；区域总监看大区 |

**关键设计点**：
- 角色层级与组织架构同步：当组织调整时权限要能自动联动
- 数据权限是 B 端 PM 最容易漏的设计点
- 多公司 / 多法人主体隔离（集团版常见需求）

### 3.3 C 端消费产品（电商 / 社交 / 内容）

| 维度 | 设计要点 |
|------|----------|
| **权限模型** | 多为 ACL + 简单 RBAC（普通用户 / VIP / 管理员） |
| **用户来源** | 自助注册、第三方登录、手机号 |
| **角色定义** | 角色少且稳定，重点是"用户身份"（VIP 等级、会员状态） |
| **角色继承** | 通常无继承关系 |
| **数据权限** | 用户只能操作自己的数据（我的订单、我的相册） |
| **权限获取** | 多与付费 / 等级 / 任务挂钩（升级 VIP 解锁功能） |
| **隐私权限** | 用户可控制内容可见范围（公开 / 好友 / 私密） |
| **典型示例** | 微信朋友圈可见范围；抖音发布权限；淘宝会员等级权益 |

**关键设计点**：
- 权限主要服务"会员体系"和"隐私保护"，而非组织管理
- 权限获取路径要平滑（试用 → 付费 → 升级）
- 用户隐私权限是合规重点（《个人信息保护法》）

### 3.4 SaaS 多租户平台（飞书 / 钉钉 / Notion）

| 维度 | 设计要点 |
|------|----------|
| **权限模型** | RBAC + ReBAC 混合（团队/空间的关系型权限） |
| **租户隔离** | 数据物理或逻辑隔离，租户间绝不互通 |
| **角色层级** | 三层：平台管理员 → 租户管理员 → 租户内用户 |
| **应用权限** | 第三方应用接入需 OAuth 授权（用户授权 / 租户管理员授权） |
| **资源粒度** | 文档 / 文件夹 / 工作区 / 项目多层级继承 |
| **协作权限** | 单文档可分享给特定人、链接、组织（这是 ReBAC 典型场景） |
| **典型示例** | Notion 页面分享；飞书文档协作；Slack 频道权限 |

**关键设计点**：
- 租户隔离是底线，数据泄漏是致命事故
- "链接分享"这种介于私密与公开之间的状态要特别设计
- 第三方应用权限回收（撤权）要可追溯

### 3.5 开放平台 / API 平台（微信开放平台 / 阿里云）

| 维度 | 设计要点 |
|------|----------|
| **权限模型** | PBAC + OAuth 2.0 Scope |
| **权限主体** | 应用（AppID）而非自然人 |
| **权限粒度** | API 级别（scope），如 `snsapi_userinfo`、`order:read` |
| **授权流程** | 用户授权 → 平台颁发 Token → 应用凭 Token 调用 API |
| **Token 机制** | Access Token（短期）+ Refresh Token（长期） |
| **权限回收** | 用户可随时撤销对某应用的授权 |
| **配额限制** | 不仅有权限，还有调用频次限制（QPS / 日调用量） |
| **典型示例** | 微信公众号 scope；GitHub OAuth App；阿里云 RAM |

**关键设计点**：
- Scope 设计要"最小必要"，避免过度授权
- Token 安全：防泄露、防重放、可吊销
- 配额管理：免费版 / 付费版分级

### 3.6 AI 产品（LLM 应用 / Agent 平台 / RAG 知识库）

这是 AI 时代的新权限设计挑战：

| 维度 | 设计要点 |
|------|----------|
| **权限模型** | RBAC + ABAC + 内容权限三层叠加 |
| **模型访问权限** | 谁能用 GPT-4 / 谁只能用 GPT-3.5（成本控制） |
| **Token 配额** | 每用户/团队每日 token 上限（成本可控） |
| **知识库权限** | RAG 检索时要叠加数据权限（用户只能查到自己有权的文档） |
| **工具调用权限** | Agent 调用 Function / Tool 时要校验权限（能否调发送邮件？） |
| **Prompt 权限** | 系统级 Prompt、知识库、模型参数的可见和修改权限 |
| **审计要求** | AI 操作（特别是涉及数据外发、工具调用）必须留痕 |
| **典型示例** | ChatGPT Plus 才能用 GPT-4；企业知识库按部门检索；Agent 调用 SAP 系统需审批 |

**AI 产品特有的权限难点**：
1. **RAG 召回要过权限过滤**：向量库召回结果必须用文档权限再过滤一遍，否则会出现"用户问一个问题，AI 把无权访问的文档内容泄露出来"
2. **Agent 自主操作的权限边界**：Agent 自动发邮件、改数据，需要"人在回路（Human-in-the-loop）"审批
3. **Prompt 注入导致的越权**：恶意用户通过 Prompt 诱导模型输出无权访问的内容，需要内容侧兜底
4. **多模型路由的权限**：不同用户走不同模型，权限设计要联动路由层

### 3.7 异同对比总表

| 对比项 | B 端企业 | C 端消费 | SaaS 平台 | 开放平台 | AI 产品 |
|--------|----------|----------|-----------|----------|---------|
| 主流模型 | RBAC | ACL+RBAC | RBAC+ReBAC | PBAC+OAuth | RBAC+ABAC+内容 |
| 角色数量 | 多 | 少 | 中 | 应用维度 | 中 |
| 角色继承 | 强 | 无 | 中 | 无 | 中 |
| 数据权限 | 必须 | 弱（自身数据） | 必须（租户隔离） | 弱 | 必须（RAG 过滤） |
| 权限获取 | 上级分配 | 付费/等级 | 租户管理员分配 | 用户授权 | 配额+角色 |
| 互斥角色 | 必须 | 无 | 可选 | 无 | 推荐 |
| 审计要求 | 高 | 中 | 高 | 高 | 极高 |
| 隐私权限 | 弱 | 强 | 中 | 强 | 高 |
| 配额限制 | 无 | 弱 | 中 | 强 | 必须（token） |
| 典型难点 | 组织联动 | 隐私合规 | 租户隔离 | Scope 设计 | RAG 越权 |

## 四、权限设计标准流程

### 4.1 PM 设计权限的五步法

```
1. 梳理资源      → 列出所有受控资源（页面/菜单/按钮/API/数据）
2. 定义操作      → 每个资源支持哪些操作（查看/创建/编辑/删除/导出/审批）
3. 设计角色      → 从业务场景反推角色（不是从组织架构硬套）
4. 建权限矩阵    → 角色 × 资源 × 操作 的三维矩阵
5. 补数据权限    → 在功能权限之上叠加数据范围过滤
```

### 4.2 权限矩阵模板

权限矩阵是 PM 与研发对齐的核心交付物，建议用表格表达：

| 角色 | 订单-查看 | 订单-创建 | 订单-编辑 | 订单-删除 | 订单-导出 | 客户-查看 | 客户-编辑 |
|------|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| 普通销售 | 本人 | ✓ | 本人 | ✗ | ✗ | 本人 | ✗ |
| 销售经理 | 本团队 | ✓ | 本团队 | ✗ | 本团队 | 本团队 | 本团队 |
| 区域总监 | 大区 | ✓ | 大区 | ✗ | 大区 | 大区 | 大区 |
| 财务 | 全部 | ✗ | ✗ | ✗ | 全部 | 全部 | ✗ |
| 管理员 | 全部 | ✓ | 全部 | ✓ | 全部 | 全部 | 全部 |

**说明**：单元格内不仅写"✓/✗"，还要标注数据范围（本人/本团队/本区/全部），这是 PM 最常漏的细节。

### 4.3 角色设计的常见原则

1. **角色数量适中**：建议 5-10 个核心角色，超过 15 个考虑引入角色组
2. **角色名要业务化**：用"销售经理"而非"role_001"
3. **角色与岗位分离**：岗位是组织概念，角色是权限概念，一个岗位可对应多角色
4. **避免权限堆叠**：一人多角色时权限是"并集"还是"交集"要明确
5. **预留自定义角色**：标准角色 + 自定义角色（租户管理员可创建）满足个性化

### 4.4 数据权限的四种实现方式

| 方式 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **组织架构过滤** | 按部门树过滤 | 简单直观 | 部门调整时数据错乱 |
| **数据标签** | 给数据打标签，按标签过滤 | 灵活 | 标签维护成本高 |
| **行级权限** | 数据库层强制过滤 | 安全 | 性能影响、SQL 复杂 |
| **业务规则** | 自定义规则（如"只能看自己创建的"） | 灵活 | 规则散落难维护 |

## 五、权限系统的技术实现要点

PM 不必精通代码，但要理解以下关键点，便于与研发沟通：

### 5.1 前后端权限校验

- **前端权限**：控制按钮 / 菜单显隐，提升体验（用户看不见 = 不能点）
- **后端权限**：真正生效的安全防线（前端可被绕过，后端不可省）
- **原则**：前端做交互层过滤，后端做安全层校验，**两者都要做**

### 5.2 Token 机制选型

| 方案 | 适用 | 特点 |
|------|------|------|
| Session + Cookie | 传统 Web | 服务端存状态，扩展性差 |
| JWT | 前后端分离、移动端 | 无状态，自包含，但难主动失效 |
| OAuth 2.0 Token | 开放平台 | 标准化，支持 scope、refresh |
| API Key | 服务间调用 | 长期有效，需配合 IP 白名单 |

### 5.3 权限缓存

权限校验是高频操作，每次查 DB 会拖垮系统：
- **缓存策略**：用户权限加载到 Redis，TTL 5-30 分钟
- **失效策略**：权限变更时主动清除对应用户缓存
- **预加载**：登录时一次性加载所有权限，避免逐接口查询

### 5.4 权限审计日志

至少记录以下信息：

```
{
  "user_id": "u_001",
  "role": "sales_manager",
  "action": "export_order",
  "resource": "order_list",
  "data_scope": "team_beijing",
  "result": "success",
  "timestamp": "2026-08-14T10:30:00Z",
  "ip": "1.2.3.4",
  "user_agent": "..."
}
```

## 六、权限设计常见陷阱

### 6.1 越权漏洞

| 类型 | 说明 | 案例 |
|------|------|------|
| **水平越权** | 同级别用户间互相访问数据 | 改 URL 中的 order_id 看到别人订单 |
| **垂直越权** | 普通用户访问管理员功能 | 抓包改 API 路径调用管理接口 |
| **IDOR**（不安全直接对象引用） | 通过遍历 ID 访问无权资源 | `/api/user/123` 改成 `/api/user/124` |

**防范**：每个 API 都要校验"当前用户对该资源的权限"，不能只校验"能否调用此接口"。

### 6.2 角色爆炸

某系统上线 3 年后角色从 5 个膨胀到 200 个，权限矩阵变成无人敢改的"雷区"。

**防范**：
- 角色与权限解耦，引入"权限组"概念
- 定期清理无用角色
- 角色变更需走评审流程

### 6.3 权限变更不生效

用户被取消权限后仍能操作，常见原因：
- Token 未刷新（JWT 中嵌了权限）
- 前端缓存未清
- 权限校验只在前端做

**防范**：
- JWT 中只放 user_id，不放权限，权限实时查后端
- 关键操作二次校验（如删除前再查一次权限）

### 6.4 默认权限过大

新用户默认拥有过多权限，违反"最小权限原则"。

**防范**：
- 新用户默认无任何权限
- 新功能上线默认对所有人关闭，按需开启
- 提供"权限申请"流程而非"权限分配"

### 6.5 权限与业务流程脱节

权限设计只考虑了"能不能做"，没考虑"什么时候能做"。

举例：订单已审批通过后，制单人仍能修改订单 → 业务流程漏洞。

**防范**：权限与状态机结合，根据资源状态动态调整可执行操作。

## 七、实战案例

### 案例1：B 端 CRM 的权限设计

**背景**：某 SaaS CRM 产品，客户为中小制造企业，需支持多部门、多销售团队协作。

**角色定义**：

| 角色 | 权限范围 |
|------|----------|
| 系统管理员 | 全部配置权限 |
| 销售总监 | 全部业务数据查看 |
| 区域经理 | 本区域数据查看 + 编辑 |
| 销售 | 本人数据查看 + 编辑 |
| 售后客服 | 客户信息查看（脱敏电话） |
| 财务 | 订单 + 回款数据查看 |

**数据权限**：基于组织架构树，自动按"本人 → 本团队 → 本部门 → 本区域 → 全公司"五级过滤。

**踩坑经验**：
- 早期只做了功能权限，销售 A 通过搜索能找到销售 B 的客户 → 补数据权限
- 角色变更后未清缓存，离职销售 1 小时内仍能访问 → 加主动缓存失效
- 售后客服能看到完整电话号码 → 加字段级脱敏权限

### 案例2：AI 知识库问答产品的权限设计

**背景**：某企业内部 AI 知识库，员工可通过对话提问，AI 从知识库检索回答。

**三层权限叠加**：

1. **基础功能权限**（RBAC）：谁能用、能用 GPT-4 还是 GPT-3.5
2. **知识库权限**（ABAC）：按部门 / 项目 / 密级控制文档可见性
3. **内容输出权限**：回答中引用的文档要叠加权限校验，无权文档不能引用

**关键设计**：
- **检索阶段**：向量召回 top_k=20 后，用文档权限过滤，保留有权访问的文档
- **生成阶段**：Prompt 中只包含过滤后的文档，避免模型"幻觉"出无权内容
- **审计**：每次问答记录用户、问题、引用文档、模型、token 消耗
- **配额**：普通员工每日 100 次提问 / 50 万 token，高管无限制

**踩坑经验**：
- 早期 RAG 不过滤权限，员工通过提问套出薪酬文档内容 → 紧急加检索过滤
- Agent 自动发邮件功能上线后，有人用 Prompt 诱导 Agent 给全员发邮件 → 加 Human-in-the-loop 审批

## 八、权限设计 Checklist

PM 评审权限方案时逐项检查：

- [ ] 所有受控资源已梳理（页面/菜单/按钮/API/数据）
- [ ] 每个资源定义了操作类型（查看/创建/编辑/删除/导出/审批）
- [ ] 角色从业务场景反推，而非照搬组织架构
- [ ] 权限矩阵已输出（含数据范围标注）
- [ ] 数据权限已设计（不只是功能权限）
- [ ] 互斥角色已识别（制单/审批分离等）
- [ ] 默认权限遵循最小权限原则
- [ ] 权限变更流程已定义（谁能改、怎么审批）
- [ ] 前后端权限校验都已规划
- [ ] 权限审计日志字段已定义
- [ ] 权限缓存与失效策略已与研发对齐
- [ ] 越权风险已评估（水平/垂直越权）
- [ ] 多端登录、Token 失效等边界场景已考虑
- [ ] 新角色 / 新功能的扩展性已验证
- [ ] 与合规要求（个保法、SOC2 等）对齐

## 九、PM 与研发协作要点

1. **PM 交付物**：权限矩阵表、角色定义文档、数据权限规则、审计字段清单
2. **研发交付物**：权限校验中间件、权限管理后台、审计日志查询接口
3. **联调重点**：越权测试用例（特别是 IDOR、水平越权）
4. **上线前**：必须做权限回归测试，覆盖每个角色 × 每个关键操作
5. **上线后**：监控异常权限调用（如非工作时间的高权限操作告警）
