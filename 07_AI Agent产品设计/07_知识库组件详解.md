## 一、知识库在 RAG 系统中的定位

### 1.1 RAG 系统的核心组件

一个完整的 RAG 系统由以下组件构成：

```
用户查询 → [Embedding 模型] → [知识库] → [Rerank] → [LLM] → 回答
                                    ↑
                              文档预处理（分块/清洗）
```

**知识库**是 RAG 的"数据底座"，承载两个核心职责：

| 职责 | 说明 |
|------|------|
| **存储** | 存储向量化后的文档块（embedding）+ 原始文档元数据 |
| **检索** | 根据查询向量快速找到最相似的 top_k 文档块 |

### 1.2 知识库 vs 传统数据库

| 维度 | 传统关系型数据库 | 知识库（向量数据库） |
|------|------------------|----------------------|
| 检索方式 | 关键词精确匹配（SQL WHERE） | 语义相似度（cosine / L2） |
| 存储内容 | 结构化数据 | 高维向量（通常 768~2048 维） |
| 适用场景 | 事务处理、报表 | 语义搜索、RAG、推荐召回 |
| 典型指标 | QPS、事务一致性 | 检索延迟、召回率、索引构建速度 |

## 二、知识库的 6 大类别

按技术原理和功能定位，知识库可分为以下 6 类：

### 类别 1：向量数据库（Vector Database）

**核心能力**：存储 embedding 向量，提供高效的相似度检索。

**代表产品**：Milvus、Pinecone、Weaviate、Qdrant、Chroma、FAISS、pgvector

**技术原理**：
- 将文本块通过 Embedding 模型转为高维向量（如 768 维）
- 向量数据库建立索引（HNSW、IVF、PQ 等）加速最近邻搜索
- 查询时对用户问题做同样的 Embedding，用 ANN（Approximate Nearest Neighbor）快速定位 top_k 相似向量

**关键指标**：
| 指标 | 说明 | 典型范围 |
|------|------|----------|
| 索引构建速度 | 建索引耗时 | 100万条/分钟 ~ 1亿条/小时 |
| 查询延迟 | 单次检索耗时 | P95: 10ms ~ 100ms |
| Recall@k | top_k 召回率 | ≥ 95%（ANN 索引） |
| 索引大小 | 磁盘/内存占用 | 向量数 × 维度 × 4字节 + 索引开销 |

### 类别 2：全文检索引擎（Full-Text Search Engine）

**核心能力**：基于关键词的精确匹配与 BM25 排序。

**代表产品**：Elasticsearch、OpenSearch、Apache Solr、BM25（库）

**技术原理**：
- 倒排索引（Inverted Index）：词 → 文档ID列表
- BM25 算法：基于词频（TF）和逆文档频率（IDF）的相关性排序
- 支持分词（jieba、IK、SmartCN）、同义词扩展

**关键指标**：
| 指标 | 说明 | 典型范围 |
|------|------|----------|
| 索引构建 | 建倒排索引速度 | 10万条/秒 |
| 查询延迟 | 关键词检索耗时 | P95: 5ms ~ 30ms |
| 检索精度 | 关键词匹配准确率 | 近 100%（精确匹配场景） |

### 类别 3：混合检索引擎（Hybrid Search Engine）

**核心能力**：将向量检索与全文检索融合，取两者之长。

**代表产品**：ES 8.x + 向量能力、Weaviate Hybrid、Qdrant Hybrid、自建（vector + BM25 + RRF）

**融合策略**：

| 策略 | 说明 | 适用 |
|------|------|------|
| **加权融合** | `score = α × vector_score + (1-α) × bm25_score` | 简单场景 |
| **RRF**（Reciprocal Rank Fusion） | 按排名融合，`score = Σ 1/(k + rank_i)` | 目前主流 |
| **级联融合** | 先 BM25 粗筛，再向量精排 | 高 QPS 场景 |
| **多路召回** | 不同检索方式并行召回，合并去重 | 追求覆盖率 |

### 类别 4：图数据库（Graph Database）

**核心能力**：存储实体与关系，支持关联路径检索。

**代表产品**：Neo4j、Amazon Neptune、JanusGraph、TuGraph

**RAG 中的作用**：构建知识图谱，补充向量检索的"关联推理"能力。

**典型场景**：
- 故障排查：告警 A → 依赖 → 服务 B → 变更 C（通过图遍历找根因）
- 企业知识：产品 → 模块 → 负责人 → 文档（多跳关系检索）

### 类别 5：文档存储（Document Store）

**核心能力**：存储原始文档，与向量库配合保存元数据。

**代表产品**：MongoDB、Elasticsearch、PostgreSQL、CockroachDB

**RAG 中的作用**：
- 存储文档原文与分块内容
- 存储向量检索的元数据（文档ID、权限标签、更新时间）
- 支持按标签过滤（权限、业务线、环境）

### 类别 6：向量文件格式（Vector File Format）

**核心能力**：离线存储与交换向量数据的文件格式。

**代表产品**：Parquet、FAISS Index File、HDF5、Apache Arrow

**用途**：向量数据的备份、迁移、离线分析、跨系统共享。

## 五、进阶架构：混合检索 + Rerank

### 5.1 为什么需要混合检索

单独的向量检索或关键词检索都有盲区：

| 场景 | 向量检索 | 关键词检索 | 混合检索 |
|------|----------|------------|----------|
| 用户问 "Redis 内存淘汰策略" | ✓ 语义匹配好 | ✗ 可能漏匹配 | ✓ 最优 |
| 用户输入精确 ID "ORD-2024-001" | ✗ 语义不匹配 | ✓ 精确命中 | ✓ 最优 |
| 新术语/新产品名 | ✗ 模型可能不认识 | ✓ 精确匹配 | ✓ 最优 |
| 口语化提问 | ✓ 语义理解 | ✗ 关键词不匹配 | ✓ 最优 |

### 5.2 混合检索架构

```
用户查询
   │
   ├──→ [向量检索] → top_k1 候选
   │
   ├──→ [BM25 检索] → top_k2 候选
   │
   └──→ [RRF 融合] → 合并去重 → top_k 候选
                                   │
                                   ▼
                          [Rerank 重排序] → 最终 top_n
```

### 5.3 RRF（Reciprocal Rank Fusion）实现

```python
def rrf(rank_lists, k=60):
    """
    多路召回的 RRF 融合
    rank_lists: [[doc_id_1, doc_id_2, ...], [doc_id_3, ...], ...]
    k: 平滑参数，通常取 60
    """
    scores = {}
    for rank_list in rank_lists:
        for rank, doc_id in enumerate(rank_list, 1):
            scores[doc_id] = scores.get(doc_id, 0) + 1.0 / (k + rank)
    # 按得分排序
    return sorted(scores.keys(), key=lambda x: scores[x], reverse=True)
```

### 5.4 Rerank 重排序

Rerank 用 Cross-Encoder（交叉编码器）对召回结果做精排，大幅提升有效召回率。

| Rerank 模型 | 开发方 | 特点 | 适用 |
|-------------|--------|------|------|
| bge-reranker-large | BAAI | 中文优秀、开源 | 中文 RAG |
| bge-reranker-m3 | BAAI | 多语言、多粒度 | 国际化场景 |

## 六、性能测试方法

### 6.1 核心性能指标

| 指标 | 说明 | 测试方法 |
|------|------|----------|
| **索引构建时间** | 建索引耗时 | 记录从开始建索引到完成的时间 |
| **查询延迟** | P50 / P95 / P99 | 用真实查询集压测 |
| **召回率 Recall@k** | top_k 中包含真实相关文档的比例 | 用标注好的 query-doc 对测试 |
| **精确率 Precision@k** | top_k 中相关文档的占比 | 同上 |
| **写入吞吐量** | 每秒可写入的向量数 | 持续写入压测 |
| **资源占用** | CPU / 内存 / 磁盘 | 监控系统指标 |

### 6.2 压测方案示例

```python
# 压测脚本示例
import time
import statistics

def benchmark_query(queries, vector_db, k=5):
    latencies = []
    recalls = []
    for query, relevant_docs in queries:
        start = time.time()
        results = vector_db.search(query, k=k)
        latency = time.time() - start
        latencies.append(latency)
        
        # 计算 Recall
        retrieved_ids = [r.id for r in results]
        hit = len(set(retrieved_ids) & set(relevant_docs))
        recall = hit / len(relevant_docs)
        recalls.append(recall)
    
    return {
        "p50_latency": statistics.median(latencies),
        "p95_latency": sorted(latencies)[int(len(latencies)*0.95)],
        "avg_recall": sum(recalls) / len(recalls),
    }
```

### 6.3 性能基准参考值

| 指标 | 小规模（10万向量） | 中规模（1000万向量） | 大规模（1亿向量） |
|------|-------------------|---------------------|------------------|
| 索引构建 | < 1 分钟 | 10~30 分钟 | 数小时 |
| 查询 P95 | 5~15ms | 15~40ms | 30~100ms |
| Recall@10 | ≥ 99% | ≥ 97% | ≥ 95% |
| 写入吞吐 | 1万+/s | 5万+/s | 10万+/s |

## 七、常见问题与陷阱

### 7.1 索引构建后查询慢

| 原因 | 解决方案 |
|------|----------|
| 索引参数过于保守 | 增大 HNSW 的 M 和 efConstruction |
| 向量维度太高 | 用 PCA 降维到 256~768 |
| 没有用 ANN 索引 | 从 Flat 切换到 HNSW/IVF |

### 7.2 召回率低

| 原因 | 解决方案 |
|------|----------|
| Embedding 模型不匹配业务领域 | 换领域优化的模型（如 BGE-M3 中文） |
| top_k 太小 | 增大 top_k（10→20→50） |
| 文档分块不合理 | 调整 chunk_size 和 overlap |
| 语义 + 关键词都需要 | 引入混合检索 |
| 召回结果排序不准 | 加 Rerank 精排 |

### 7.3 数据不一致

| 原因 | 解决方案 |
|------|----------|
| 向量库和文档库不同步 | 引入事务性写入或 CDC |
| 元数据更新未同步到向量 | 设计统一的写入管道 |
| 删除操作未真正删除 | 定期一致性校验 |

### 7.4 成本失控

| 原因 | 解决方案 |
|------|----------|
| 向量规模无限增长 | 设置保留策略，归档冷数据 |
| 查询 QPS 无上限 | 加缓存 + 限流 |
| 使用高成本模型 | 冷热分离：热数据用高精度模型，冷数据用低成本模型 |

## 八、AIOPS Troubleshooting 项目推荐方案

结合本 PRD 项目的特点（故障知识库、需权限过滤、需关联分析），推荐以下组合：

```
┌────────────────────────────────────────────────────┐
│                  AIOPS 知识库方案                      │
├────────────────────────────────────────────────────┤
│                                                      │
│  主存储：Milvus（向量检索）                           │
│  ├── 存储：故障案例、SOP、架构文档的向量              │
│  ├── 索引：HNSW                                      │
│  ├── 规模：初始 50 万，预计年增长 200 万              │
│  └── 检索：top_k=10，配合 Rerank                      │
│                                                      │
│  辅助存储：Elasticsearch（全文 + 元数据）              │
│  ├── 存储：原始文档、权限标签、时间戳                 │
│  ├── 作用：关键词检索 + 权限过滤 + 混合检索           │
│  └── 混合策略：RRF 融合                               │
│                                                      │
│  可选增强：Neo4j（服务拓扑图）                        │
│  ├── 存储：服务依赖关系、变更关联                     │
│  └── 作用：故障根因关联分析                           │
│                                                      │
│  Rerank：bge-reranker-large（中文优化）                │
│                                                      │
│  Embedding：bge-m3（多语言、多粒度）                  │
│                                                      │
└────────────────────────────────────────────────────┘
```

**选型理由**：
1. **Milvus** 承载核心向量检索，性能可满足中长期规模
2. **ES** 补全关键词检索和元数据过滤（按业务线/环境/权限）
3. **RRF 融合** 兼顾语义和关键词双路召回
4. **bge-reranker** 中文场景下的 Rerank 效果业界领先
5. **可选 Neo4j** 支持故障关联路径分析（如：告警 A → 依赖服务 B → 最近变更）

## 九、习题自测

1. 你的产品需要支持"按标签过滤的语义检索"（如只检索当前用户有权访问的文档）。向量数据库本身能解决这个问题吗？如果不能，应该如何设计？
