# RAG 知识库

> 所属维度：AI 专项能力 ｜ 参考分：72

## 一、能力定义

RAG（Retrieval-Augmented Generation，检索增强生成）是让大模型**先从私有知识库检索相关资料，再基于资料生成回答**的技术方案。

RAG 能力指 PM 能设计这套系统的产品形态、知识策略、检索逻辑与质量指标，解决"模型不知道企业内部知识、会幻觉"的问题。

## 二、为什么需要 RAG

| 纯大模型的问题 | RAG 如何解决 |
|----------------|--------------|
| 不知道企业私有/最新知识 | 实时检索内部知识库 |
| 会编造事实（幻觉） | 基于检索到的真实内容回答，可附来源 |
| 微调成本高、更新慢 | 更新知识库即可，无需重新训练 |
| 无法溯源 | 回答可引用具体文档 |

**RAG vs 微调**：知识频繁更新、需要溯源 → RAG；需要改变模型风格/习得固定技能 → 微调。多数企业知识问答场景首选 RAG。

## 三、RAG 完整流程

### 3.1 离线索引（知识入库）
```
原始文档（PDF/Word/网页/工单/代码…）
  → 解析清洗（提取文本、去噪）
  → 分块（Chunking）
  → Embedding（向量化）
  → 存入向量数据库（+ 原文/元数据存文档库）
```

### 3.2 在线检索回答
```
用户问题
  → 查询处理（改写/扩展/HyDE）
  → 向量化
  → 向量检索（+ 关键词 BM25 混合检索）
  → Rerank 精排
  → 取 Top-K 片段拼入 Prompt
  → LLM 生成回答（带来源引用）
```

## 四、PM 必须掌握的关键设计

### 4.1 分块策略（Chunking）
- **块太大**：主题混杂、检索不精、浪费 token
- **块太小**：语义不完整、断章取义
- 常见做法：按标题/段落切，500-1000 字/块，块之间留重叠（overlap，如 10-20%）
- 结构化文档（FAQ、表格）按其结构切

### 4.2 Embedding 模型
- 把文本转为高维向量，决定"语义相似度"质量
- 中文场景选中文/多语言优化模型（如 bge-m3、bge-large-zh）
- **注意**：查询和文档必须用同一个 embedding 模型，换模型要全量重建向量

### 4.3 检索方式
- **向量检索**：语义相似（"内存溢出"能匹配到"OOM"）
- **关键词检索（BM25/ES）**：精确匹配（专有名词、错误码、ID）
- **混合检索（Hybrid）**：两者结合 + RRF 融合，生产环境推荐——纯向量对专有名词、编号类查询常漏召回

### 4.4 Rerank（重排序）
召回阶段先取较多候选（如 Top-20/50），再用 Cross-Encoder 精排模型（如 bge-reranker）按与问题的真实相关性重排取 Top-5，显著提升有效命中。

### 4.5 查询处理
- 查询改写（口语→规范表达）
- 多查询扩展（一个问题生成多个角度分别检索）
- HyDE（先生成假设答案，用答案向量去检索）
- 意图识别（问答 / 检索文档 / 闲聊分流）

### 4.6 知识库运营（易被忽视）
- 知识更新机制：增量入库、失效文档下线、版本管理
- 知识质量：去重、清洗、权限标签
- 冷启动：首批高质量知识的整理
- 反馈闭环：点踩/无答案 case → 补充知识库

## 五、核心指标

| 指标 | 含义 |
|------|------|
| 召回率 Recall@K | 相关文档是否被检索到（"找全"）|
| 精确率 Precision@K | 检索结果中相关的占比（"找准"）|
| 命中率 | 回答能引用到相关知识的比例 |
| 上下文相关性 | 送入 LLM 的片段与问题的相关程度 |
| 回答忠实度 | 回答是否忠于检索内容（不编造） |
| 端到端延迟 | 检索+生成总耗时 |
| 无答案率 | 知识库覆盖不到的问题比例 |

详见 [06_召回与召回率详解.md](../../01_AI技术基础/06_召回与召回率详解.md) 与 [06_模型评估.md](06_模型评估.md)。

## 六、提升效果的 8 种手段

1. 调整 Top-K（增大召回覆盖）
2. 优化分块（大小、重叠、按结构）
3. 换更好的 embedding 模型
4. 向量 + BM25 混合检索
5. 加 Rerank 精排
6. 查询改写/扩展
7. 元数据过滤（业务线、时间、权限）
8. 领域微调 embedding / 补充知识库

## 七、产品设计要点

- **展示来源**：回答附引用，点击可跳转原文，建立信任与可核验性
- **无答案兜底**：知识库没有时明确说"未找到"，而不是硬编
- **权限继承**：检索必须叠加用户权限过滤，防止越权看到无权文档（详见[产品权限设计](../../03_AI产品设计/06_产品权限设计详解.md)）
- **反馈入口**：有用/无用、纠错，反哺知识运营
- **多轮上下文**：结合对话历史改写当前查询

## 八、常见误区

| 误区 | 后果 |
|------|------|
| 只做向量检索不做混合 | 专有名词/编号类查询漏召回 |
| 分块拍脑袋、不做对比实验 | 召回率低且不知原因 |
| 知识库"一建了之"不运营 | 知识过期、覆盖差 |
| 不做权限过滤 | 数据越权泄露 |
| 只看回答主观感觉，不测召回率 | 无法系统性优化 |
| 频繁换 embedding 不重建索引 | 检索结果错乱 |
| 把所有问题都塞给 LLM 上下文 | 成本高、中间内容被忽略 |

## 九、实战案例（AIOPS 知识库）

- 知识来源：历史故障工单、SOP、架构文档、变更记录
- 架构：Milvus（向量）+ Elasticsearch（关键词+元数据）混合检索，RRF 融合，bge-reranker 精排
- 权限：按业务线/环境过滤
- 优化目标：Top-3 召回率 ≥ 85%
- 详见 [07_知识库组件详解.md](../../07_AI%20Agent产品设计/07_知识库组件详解.md)
