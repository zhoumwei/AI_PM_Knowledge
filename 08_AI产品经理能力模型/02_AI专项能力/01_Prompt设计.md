# Prompt 设计

> 所属维度：AI 专项能力 ｜ 参考分：70

## 一、能力定义

Prompt 设计（提示工程，Prompt Engineering）是通过**设计输入指令**，引导大语言模型稳定、准确、可控地输出期望结果的能力。

对 AI PM 而言，Prompt 不是"写一句话"，而是产品逻辑的一部分——它定义了 AI 的角色、任务、边界、输出格式和安全策略。

## 二、为什么重要

- Prompt 直接决定 AI 产品的**输出质量下限**，同样的模型，好 Prompt 和差 Prompt 效果可差数倍。
- Prompt 是**成本最低的优化手段**：不用换模型、不用训练，改文字即可见效。
- Prompt 是产品意图的"翻译器"：把业务规则翻译成模型能遵守的指令。
- 但 Prompt 不是万能的：它无法突破模型本身的知识与能力边界。

## 三、Prompt 的核心构成

一个结构化的生产级 Prompt 通常包含：

```
# 角色（Role）：你是谁
# 任务（Task）：要做什么
# 背景/上下文（Context）：相关信息
# 规则/约束（Constraints）：必须遵守/禁止的事
# 输入数据（Input）：待处理内容
# 输出格式（Output Format）：JSON/Markdown/字段定义
# 示例（Few-Shot）：1-3 个输入输出样例
# 兜底指令（Fallback）：做不到时怎么办
```

## 四、关键技巧

### 4.1 角色设定
赋予模型明确身份可激活相关能力："你是一名有 10 年经验的资深 SRE…"比直接提问更专业。

### 4.2 任务拆解与明确化
- 一次只让模型做一件清晰的事；复杂任务拆成多步。
- 用动词开头、可衡量："列出 3 个最可能的根因，按置信度排序"优于"分析一下"。

### 4.3 Few-Shot（少样本示例）
给 1-3 个"输入→期望输出"示例，比抽象描述规则更有效，尤其对输出格式和风格要求高的场景。

### 4.4 思维链（CoT）
要求模型"先逐步推理，再给结论"（"让我们一步一步思考"），可显著提升复杂推理任务准确率。进阶变体：
- **ToT（Tree of Thoughts）**：多路径探索
- **ReAct**：推理（Reasoning）+ 行动（Acting）交替，Agent 基础模式
- **Self-Consistency**：多次采样取一致结论

### 4.5 结构化输出
要求输出固定 JSON，便于程序解析：
```
请严格输出以下 JSON，不要输出任何额外文字：
{"root_causes": [{"cause": "...", "confidence": "high|medium|low", "evidence": "..."}]}
```

### 4.6 SOP 流程约束（AI PM 高阶）
用专家经验流程模板约束模型推理路径，防止自由发挥导致幻觉。这是 CCF 2025 根因定位冠军方案的核心思路：
```
严格遵循以下 SOP：
1. 解析告警：提取告警源、对象、指标、阈值、时间
2. 证据收集：调用工具检索日志/指标/变更/拓扑
3. 因果推断：区分"相关性"与"因果性"
4. 输出候选：每个候选必须附具体证据
若证据不足，明确说明需要补充什么，不要臆测。
```

### 4.7 边界与兜底
- 明确禁止项："不得执行未列出的操作""不得编造数据"
- 定义拒答："当问题与运维无关时，礼貌拒绝"
- 低置信度处理：要求模型自评把握程度

## 五、Prompt 设计流程

```
明确目标与输出 → 写初版 Prompt → 构造测试集（20-50 条）
  → 跑批评测 → 分析 bad case → 迭代 Prompt（每次只改一个变量）
  → 版本管理 → 上线灰度 → 持续收集 bad case
```

## 六、版本管理与协作（工程化）

| 实践 | 说明 |
|------|------|
| Prompt 入代码库 | 像代码一样 Git 管理，而非写死在代码里 |
| 版本号 | prompt_v1.2，记录每次改动原因 |
| 变更评测 | 改 Prompt 必须在回归测试集上对比，防止"修好 A 弄坏 B" |
| 环境分离 | 测试/生产 Prompt 隔离 |
| 变量外置 | 动态内容（用户输入、检索结果）用占位符注入，与指令分离 |

## 七、常见问题与优化

| 问题 | 可能原因 | 优化方向 |
|------|----------|----------|
| 输出跑题 | 任务不清/无角色 | 明确角色与任务边界 |
| 格式不稳定 | 无格式约束/示例 | 加 JSON schema + Few-Shot |
| 编造事实（幻觉） | 缺少依据 | 强制引用证据 + RAG + 兜底指令 |
| 长指令失效 | 注意力分散（lost in the middle） | 关键约束放开头/结尾，精简指令 |
| 复杂推理出错 | 直接要答案 | 引入 CoT/分步 |
| 改好 A 弄坏 B | 缺回归集 | 建评测集做回归 |
| 被用户带偏 | 注入攻击 | 输入与系统指令隔离，加防注入规则 |

## 八、AI PM 的职责边界

- PM 主导：Prompt 要表达的**业务规则、输出结构、安全边界、验收标准**
- 与算法/工程协作：具体调优、版本管理实现、评测自动化
- PM 必须能读懂、评审、提出修改方向，而非完全外包给技术

## 九、实战案例（AIOPS 归因 Prompt 迭代）

- v1.0："分析这个告警的根因"→ 输出冗长、常编造、无法解析
- v1.1：加角色 + 固定 JSON 输出 → 可解析，但仍幻觉
- v1.2：加 SOP 四步 + 强制证据字段 → 幻觉下降
- v1.3：加入检索到的真实日志/变更（RAG）+ "证据不足就说明"→ 归因可信度显著提升
- 每次迭代在 50 条标注告警上回归，确认 Top-3 召回率只升不降
