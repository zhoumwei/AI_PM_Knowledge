# 接口文档

> 所属维度：技术协作能力 ｜ 参考分：60

## 一、能力定义

接口文档（API 文档）是描述"前端/调用方如何与后端交互"的契约。本能力指 PM 能**读懂接口文档、评审其合理性，并能写出或清楚描述自己需要的接口**。

接口文档是前后端协作的"合同"，也是测试用例的重要来源。

## 二、一份完整接口文档应包含

| 部分 | 内容 |
|------|------|
| 基本信息 | 接口名称、功能说明、负责人 |
| 请求方式 | GET/POST/…、URL、环境（测试/生产） |
| 鉴权要求 | 需要什么 Token/权限 |
| 请求参数 | 路径参数、query、body；字段名/类型/必填/说明/示例 |
| 请求示例 | 完整可运行的请求样例 |
| 响应结构 | 成功返回的字段、类型、含义、示例 |
| 错误码 | 各种失败的 code、message、触发场景 |
| 备注 | 限流、分页、幂等、是否异步、特殊逻辑 |

## 三、OpenAPI / Swagger 规范

业界主流的接口描述规范（Swagger 是其工具生态），可自动生成可交互文档。一个字段通常长这样：

```yaml
paths:
  /alerts/{id}:
    get:
      summary: 查询告警详情
      parameters:
        - name: id
          in: path
          required: true
          schema: { type: string }
      responses:
        '200':
          description: 成功
          content:
            application/json:
              schema:
                type: object
                properties:
                  alert_id: { type: string }
                  severity: { type: string, enum: [P1,P2,P3] }
                  status: { type: string }
```

PM 不一定要会写 YAML，但要看懂字段、类型、required、enum、responses。

## 四、PM 重点评审什么

### 4.1 字段层面
- 含义是否无歧义（同名不同义最危险）
- 类型是否合理（金额用 string/分，不用 float）
- 必填/可选是否明确
- 枚举值是否完整（状态机的所有状态都要列）
- 是否缺字段（产品要展示的信息后端给不给）

### 4.2 边界与异常
- 查不到数据返回什么（null？空数组？404？）
- 超长文本、特殊字符、分页边界（第 0 页、超大数据）
- 无权限、未登录、被限流分别返回什么
- 并发/重复提交如何处理

### 4.3 一致性
- 命名风格统一（`user_id` 不要混用 `userId`、`uid`）
- 时间格式统一（ISO 8601 + 时区，或时间戳）
- 分页参数统一、错误码结构统一
- 通用响应包裹是否统一（如 `{code, message, data}`）

### 4.4 产品逻辑可实现性
- 页面需要的信息是否都能拿到（可能要多个接口聚合）
- 排序/筛选/搜索字段是否支持
- 是否需要新增接口或字段

## 五、PM 如何描述/撰写自己需要的接口

即使不写代码，也应能用自然语言 + 字段表清楚表达需求：

```
我需要一个"查询某告警关联变更"的接口：
- 输入：告警 ID（必填）、时间范围（可选，默认告警前后 1 小时）
- 输出：变更列表，每项含：变更ID、变更人、变更时间、变更内容摘要、关联度
- 排序：按关联度降序
- 异常：无变更返回空数组；无权限返回 403
- 性能：P95 < 500ms
```
研发可据此设计具体 REST 路径与字段。

## 六、与原型/PRD 的对应关系
- 原型上每一处**需要展示的数据**，都要能在某个接口的响应里找到来源
- 每一个**用户操作**，都要能对应到一个请求
- 用一张"页面-数据-接口"对照表检查遗漏：

| 页面元素 | 数据字段 | 来源接口 |
|----------|----------|----------|
| 告警标题 | title | GET /alerts/{id} |
| 严重级别 | severity | 同上 |
| 根因列表 | root_causes[] | POST /rca |

## 七、常见误区

| 误区 | 后果 |
|------|------|
| 只看成功返回，不看错误码 | 异常态无法设计 |
| 字段含义口头约定不写文档 | 联调时各说各话 |
| 枚举值不全 | 新增状态时前后端崩溃 |
| 时间/金额/命名不统一 | 展示错误、难维护 |
| 接口文档与代码不同步 | 文档失真、误导 |
| PM 完全不看接口文档 | 到联调才发现数据缺失 |

## 八、自测题

1. 拿一份真实接口文档，指出至少 3 个可改进点（字段、边界、异常）。
2. 你的核心页面有一张"页面元素→字段→接口"对照表吗？
3. "查不到数据"应该返回 null、空数组还是 404？说明理由与适用场景。
4. 尝试用自然语言定义一个新接口，请研发同事评审。
