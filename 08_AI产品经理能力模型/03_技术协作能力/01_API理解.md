# API 理解

> 所属维度：技术协作能力 ｜ 参考分：62

## 一、能力定义

API（Application Programming Interface，应用程序编程接口）是系统之间相互调用的"约定"。API 理解能力指 PM 能看懂 API 的**请求方式、输入输出、鉴权、性能与错误处理**，从而准确评估功能可行性与边界。

## 二、为什么 PM 要懂 API

- AI 产品的核心就是"调用模型 API + 调用业务工具 API"，不懂 API 就无法设计 Agent 的工具能力。
- 能判断一个需求"技术上怎么实现、数据从哪来、能不能实时"。
- 评审时能发现字段缺失、边界没定义、性能不达标等问题，减少返工。

## 三、必须掌握的基础概念

### 3.1 RESTful API
用 HTTP 方法表达操作，用 URL 表达资源：

| 方法 | 语义 | 示例 |
|------|------|------|
| GET | 查询 | `GET /alerts/123` |
| POST | 创建 | `POST /tickets` |
| PUT | 全量更新 | `PUT /tickets/123` |
| PATCH | 部分更新 | `PATCH /tickets/123` |
| DELETE | 删除 | `DELETE /tickets/123` |

### 3.2 HTTP 状态码
| 码段 | 含义 | 常见 |
|------|------|------|
| 2xx | 成功 | 200 OK、201 Created、206 Partial Content（流式/分片）|
| 3xx | 重定向 | 301/302 |
| 4xx | 客户端错误 | 400 参数错、401 未认证、403 无权限、404 不存在、429 限流 |
| 5xx | 服务端错误 | 500、502、503、504 超时 |

### 3.3 一次 API 请求的组成
- 请求方法 + URL（含 query 参数）
- 请求头（Header）：鉴权、内容类型
- 请求体（Body）：POST/PUT 的数据，通常是 JSON
- 响应：状态码 + 响应体（JSON）

### 3.4 鉴权与安全
- API Key / Token：标识调用方身份
- OAuth 2.0：第三方授权
- 不要把密钥写在前端/明文传输（HTTPS）

### 3.5 性能与约束
- **限流（Rate Limit）**：如 100 次/分钟，超限返回 429
- **超时（Timeout）**：调用方要设超时
- **重试与幂等**：失败重试需保证重复调用不产生重复副作用（幂等键）
- **分页**：大量数据用 page/size 或 cursor

### 3.6 其他通信方式
- **gRPC**：高性能、强类型，内部服务间常用
- **Webhook**：事件发生时对方主动回调你的接口（如支付成功通知）
- **WebSocket / SSE**：服务端主动、实时/流式推送

## 四、AI 相关 API 的特殊点（重点）

### 4.1 LLM Chat API
典型请求结构（消息数组）：
```json
{
  "model": "gpt-4o",
  "messages": [
    {"role": "system", "content": "你是资深SRE…"},
    {"role": "user", "content": "分析这个告警…"}
  ],
  "temperature": 0.2,
  "stream": true
}
```
- `system`：系统指令；`user`：用户输入；`assistant`：模型历史回复
- `temperature`：低=确定，高=发散；事实任务调低

### 4.2 流式输出（stream / SSE）
- `stream: true` 时模型通过 **SSE（Server-Sent Events）** 逐 token 返回
- 前端边收边显示（打字机效果），显著改善"等待感"
- 需处理：中途断流、用户点停止、首 token 延迟

### 4.3 Token 与上下文
- 输入+输出 token 受上下文窗口限制，超限会报错或被截断
- 费用按 token 计

### 4.4 Function Calling / Tool API
模型返回"想调用的工具名 + 参数"，由外部系统执行后把结果回传。PM 需设计工具清单与 JSON Schema（详见 [Agent 产品设计](../02_AI专项能力/04_Agent产品设计.md)）。

### 4.5 Embedding API
输入文本，输出一串向量数字（embedding），用于 RAG 入库与检索。

## 五、PM 评审 API 时的检查清单

- [ ] 这个功能依赖哪个接口？数据从哪来？
- [ ] 请求/响应字段是否完整、含义是否明确？
- [ ] 必填/可选、字段类型、枚举值是否定义？
- [ ] 异常情况（空、超长、不存在、无权限）返回什么？
- [ ] 能支撑多大数据量？是否分页？
- [ ] QPS/限流/超时能否满足业务峰值？
- [ ] 鉴权方式？谁能调？有没有越权风险？
- [ ] 是同步还是异步？耗时操作如何拿结果？
- [ ] 失败重试是否幂等？
- [ ] AI 接口：是否流式？token 限制？成本？失败兜底？

## 六、实践方法

1. 用 **Postman / Apifox / curl** 实际调用 2-3 个接口（含一个 LLM API）
2. 打开浏览器 F12 → Network，观察一次真实操作背后的请求与返回
3. 让研发给你一份接口文档，尝试不依赖讲解读懂它
4. 尝试用自然语言描述一个你需要的接口，请研发点评是否合理

## 七、常见误区

| 误区 | 纠正 |
|------|------|
| 认为"数据系统里都有"就能用 | 要看有没有现成 API、字段、权限 |
| 忽视 429 限流 | 高并发要评估配额与排队 |
| 假设接口一定实时返回 | 耗时任务多为异步 |
| 不看错误码 | 4xx/5xx 的产品提示完全不同 |
| 忽视流式/中断处理 | AI 体验关键细节 |

## 八、自测题

1. 用一句话解释 GET 和 POST、401 和 403 的区别。
2. 打开 F12，描述一次"发送 AI 消息"触发了哪些请求。
3. `stream=true` 后数据是如何到达前端的？为什么这样体验更好？
4. 接口偶发超时，产品上应如何兜底？重试要注意什么？
