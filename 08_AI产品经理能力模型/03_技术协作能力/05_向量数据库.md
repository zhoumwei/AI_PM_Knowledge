# 向量数据库

> 所属维度：技术协作能力 ｜ 参考分：66

## 一、能力定义

理解向量数据库的**基本原理、主流产品、选型逻辑与使用场景**，能与研发共同完成 RAG 知识库的技术选型与效果优化。

PM 不必会运维向量库，但必须能回答"选哪个、为什么、性能与成本如何权衡"。

## 二、为什么会有向量数据库

传统数据库做"精确匹配"（SQL `WHERE name='xxx'`），无法回答语义问题（"内存溢出" 应能匹配到 "OOM""Out of Memory"）。

Embedding 模型把文本变成一串高维数字（向量，如 1024 维），**语义相近的文本向量在空间中距离也近**。向量数据库就是专门存储这些向量、并做**快速相似度检索（ANN，近似最近邻）**的系统。

## 三、核心概念

| 概念 | 含义 | PM 需要理解的点 |
|------|------|------------------|
| Embedding | 文本→向量 | 查询和文档须用同一模型 |
| 维度 | 向量长度（768/1024/1536…） | 影响存储与检索 |
| 相似度/距离 | 衡量两向量接近程度 | 决定排序 |
| ANN | 近似最近邻搜索 | 用少量精度换大幅提速 |
| 索引 | 加速检索的数据结构（HNSW、IVF、PQ） | 影响速度/内存/召回 |
| Top-K | 返回最相似的 K 条 | 与召回率、成本相关 |
| Payload/元数据 | 向量附带的标签字段 | 用于过滤（权限/时间/类别） |

### 三种常用距离度量
- **余弦相似度（Cosine）**：看方向夹角，最常用于文本语义检索
- **内积（IP/Dot Product）**：兼顾方向与长度
- **欧氏距离（L2）**：空间直线距离

## 四、主流产品对比（选型必备）

| 产品 | 形态 | 开源 | 规模 | 特点 | 适合 |
|------|------|------|------|------|------|
| **Milvus** | 独立数据库 | 是 | 十亿级 | 分布式、性能强、生态好、运维较重 | 中大型生产 RAG |
| **Pinecone** | 全托管 SaaS | 否 | 弹性 | 零运维、海外、成本较高 | 快速上线/海外业务 |
| **Weaviate** | 独立/托管 | 是 | 亿级 | 内置向量化、混合检索好 | 中等规模 |
| **Qdrant** | 独立 | 是 | 千万级 | 轻量高性能、过滤灵活、省资源 | 中小/边缘 |
| **Chroma** | 嵌入式库 | 是 | 百万级 | 极简、零运维 | 原型/个人 |
| **FAISS** | 搜索库（非数据库）| 是 | 十亿级 | 性能极高、支持 GPU，但需自行封装 | 高性能场景/二次开发 |
| **pgvector** | PostgreSQL 扩展 | 是 | 千万级 | 关系库+向量一体、事务一致 | 已有 PG、中小规模 |
| **Elasticsearch 8.x** | 搜索引擎+向量 | 是 | 亿级 | 向量+BM25 混合检索成熟 | 混合检索场景 |

## 五、选型决策维度

| 维度 | 关键问题 |
|------|----------|
| 数据规模 | 向量总量、年增长 |
| 性能 | P95 检索延迟、写入吞吐 |
| 检索方式 | 是否需要向量+关键词混合、是否需要过滤 |
| 运维能力 | 自建还是托管 |
| 成本 | 硬件/云费用、人力 |
| 数据合规 | 是否必须私有化、数据能否出境 |
| 现有技术栈 | 是否已有 PG / ES / K8s，减少新组件 |
| 生态集成 | 与 LangChain、Embedding 模型、Rerank 的兼容 |

### 典型推荐
- **生产中大型、私有化**：Milvus + Elasticsearch（混合检索）
- **已有 PostgreSQL**：pgvector 起步
- **快速验证/Demo**：Chroma
- **海外/零运维**：Pinecone
- **资源受限边缘**：Qdrant

## 六、与 RAG 的关系（产品视角）

```
文档 → 分块 → embedding → 向量库（存向量+ID+元数据）
查询 → embedding → 向量库 ANN 检索 Top-K（可叠加元数据过滤）
     →（可选）BM25 混合 + RRF 融合 → Rerank → 送 LLM
```

PM 要关注的产品级决策：
- **元数据过滤**：检索时按用户权限、业务线、环境、时间过滤（防越权）
- **混合检索**：专有名词/错误码靠 BM25，语义靠向量
- **Top-K 权衡**：K 大覆盖全但噪声多、成本高；需配合 Rerank
- **更新机制**：文档增删改后向量如何同步

## 七、性能与成本的基本判断

- ANN 索引是"速度 vs 精度 vs 内存"的权衡：索引参数激进→快但召回略降
- 维度越高、向量越多：内存与存储占用越大
- 生产关注：P95 延迟（常见十几到几十毫秒）、Recall@K（生产一般要求 ≥95% 索引层召回）、写入吞吐
- 冷数据可归档，避免规模无限膨胀

## 八、常见误区

| 误区 | 纠正 |
|------|------|
| 以为向量库能理解关键词精确匹配 | 向量弱精确匹配，需混合 BM25 |
| 换 embedding 模型不重建向量 | 必须全量重嵌入 |
| 检索不做权限过滤 | 严重数据越权风险 |
| 只选向量库不管元数据过滤 | 企业场景过滤是刚需 |
| Top-K 越大越好 | 噪声与成本上升，配 Rerank |
| 盲目上重型分布式库 | 小规模 pgvector/Chroma 足矣 |
