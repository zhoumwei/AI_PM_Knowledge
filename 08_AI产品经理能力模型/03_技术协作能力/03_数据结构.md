# 数据结构

> 所属维度：技术协作能力 ｜ 参考分：62

## 一、能力定义

这里的"数据结构"对 PM 而言，指理解**业务数据如何组织、存储、关联与查询**，包括数据库表结构、数据类型、数据流转（ETL/数仓分层），以及 AI 特有的训练/向量数据形态。

目标是能与数据/研发团队有效沟通，能自己做基础数据查询。

## 二、为什么 PM 要懂数据结构

- 数据是 AI 产品的"燃料"，懂数据才能判断需求可行性、数据是否够用。
- 能直接取数验证想法，不必事事排队等数据同学。
- 设计指标、埋点、报表时，清楚数据从哪张表、哪些字段来。

## 三、关系型数据库基础

### 3.1 表、行、列、主键、外键
- 表（Table）：一类实体（如 users、alerts、tickets）
- 行（Row）：一条记录；列（Column）：一个属性
- 主键（Primary Key）：唯一标识一行
- 外键（Foreign Key）：关联到另一张表（如 ticket 表的 `alert_id` 关联告警表）
- 表之间关系：一对一、一对多、多对多（需中间表）

### 3.2 常用字段类型
| 类型 | 用途 | 注意 |
|------|------|------|
| int/bigint | 整数、ID | 金额避免用浮点 |
| decimal | 精确金额 | 金额首选 |
| varchar/text | 字符串 | 长度设计 |
| datetime/timestamp | 时间 | 统一时区 |
| boolean | 是/否 | - |
| json/jsonb | 半结构化 | 灵活但难查询 |

### 3.3 索引
索引像书的目录，加快查询，但会占空间、拖慢写入。常为高频筛选/排序/关联字段建索引。

### 3.4 SQL 必会四件套
```sql
-- 查询 + 条件
SELECT severity, COUNT(*) FROM alerts
WHERE created_at >= '2026-10-01' AND status='closed'
GROUP BY severity;

-- 关联
SELECT t.id, a.severity
FROM tickets t JOIN alerts a ON t.alert_id = a.id;

-- 聚合：平均 MTTR（分钟）
SELECT AVG(TIMESTAMPDIFF(MINUTE, created_at, resolved_at)) AS avg_mttr
FROM tickets WHERE resolved_at IS NOT NULL;

-- 排序 + 分页
ORDER BY created_at DESC LIMIT 20 OFFSET 0;
```
重点掌握：SELECT/WHERE、JOIN、GROUP BY + 聚合（COUNT/AVG/SUM）、ORDER BY/LIMIT。

## 四、数据仓库分层（数据分析必备）

| 层 | 名称 | 内容 |
|----|------|------|
| ODS | 原始数据层 | 各业务系统原始数据，原样落地 |
| DWD | 明细数据层 | 清洗、规范化后的明细 |
| DWS | 汇总数据层 | 按主题轻度汇总（如用户日汇总）|
| ADS | 应用数据层 | 面向报表/应用的最终指标 |

数据流转：业务库 →（ETL/CDC 同步）→ ODS → DWD → DWS → ADS → 报表/BI。

- **ETL**：抽取-转换-加载（批量，如 T+1）
- **CDC**：变更数据捕获（近实时同步增量数据）

## 五、非关系型与其他存储（了解即可）

| 类型 | 代表 | 适合 |
|------|------|------|
| 文档型 | MongoDB | 结构灵活、嵌套数据 |
| KV | Redis | 缓存、会话、热点 |
| 时序库 | InfluxDB/Prometheus | 监控指标 |
| 搜索引擎 | Elasticsearch | 日志、全文检索 |
| 向量库 | Milvus | Embedding 向量（见 [向量数据库](05_向量数据库.md)） |

## 六、AI 场景特有的数据形态

### 6.1 训练/微调数据（指令格式 JSONL）
```json
{"instruction": "分析告警根因", "input": "CPU 使用率 99%…", "output": "可能是内存泄漏导致频繁GC…"}
```
- JSONL：每行一个 JSON 对象
- PM 需关注：数据规模、标注规范、质量、脱敏、训练/验证/测试集划分

### 6.2 RAG 数据
- 原始文档库（存原文、元数据）
- 向量库（存 embedding 向量 + 文档块 ID）
- 元数据：业务线、权限标签、时间、来源（用于过滤）

### 6.3 日志/事件数据
半结构化、量大、时序性强，常需解析、聚合、优先级筛选后再送 LLM（降低噪声与成本）。

## 七、数据质量与治理意识

| 维度 | 问题示例 |
|------|----------|
| 完整性 | 字段缺失、埋点漏报 |
| 准确性 | 口径错误、脏数据 |
| 一致性 | 不同系统同一指标对不上 |
| 及时性 | T+1 数据无法支撑实时场景 |
| 唯一性 | 重复记录 |

PM 在定义指标时必须对齐**数据口径**（如"活跃用户"的精确定义、"MTTR"的起止时间点）。

## 八、实践方法

1. 每周写 3 条 SQL，从自己业务的真实问题出发
2. 请数据同学带你看一次数仓表结构和血缘
3. 为你负责的核心指标画出"字段→表→报表"链路
4. 尝试自己取一次数验证一个产品假设

## 九、常见误区

| 误区 | 纠正 |
|------|------|
| 指标口径模糊（"活跃"） | 精确定义并文档化 |
| 用 float 存金额 | 用 decimal/最小货币单位整数 |
| 忽视时区和时间格式 | 统一规范 |
| 以为有数据就能训模型 | 还要看质量、标注、规模 |
| 多张表数据对不上不追根因 | 统一口径与数据源 |

## 十、自测题

1. 写出"统计上周 P1 故障平均 MTTR"的 SQL（表结构自定义）。
2. 解释 ODS/DWD/DWS/ADS 的区别与数据流向。
3. 你的核心指标（如转化率）口径是什么？数据来自哪一层？
4. RAG 系统里原文、向量、元数据分别存在哪？为什么分开？
