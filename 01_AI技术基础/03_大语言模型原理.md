# 大语言模型原理

## 一、什么是大语言模型（LLM）

大语言模型是基于Transformer架构的大规模预训练语言模型，能够理解和生成人类语言。

**核心特点**：
- **大规模参数**：数十亿到万亿级参数
- **预训练+微调**：先在海量数据上预训练，再针对特定任务微调
- **涌现能力**：随着模型规模增大，出现新的能力（如推理、多步思考）

## 二、LLM发展历程

| 模型 | 发布时间 | 参数规模 | 关键特点 |
|------|----------|----------|----------|
| GPT-1 | 2018 | 1.17亿 | 首次将Transformer用于语言模型 |
| GPT-2 | 2019 | 15亿 | 更大规模，零样本学习能力 |
| GPT-3 | 2020 | 1750亿 | 涌现能力，few-shot学习 |
| GPT-3.5 | 2022 | ~1750亿 | 对话能力，ChatGPT基础模型 |
| GPT-4 | 2023 | 未公开 | 多模态，更强推理能力 |
| LLaMA | 2023 | 7B/13B/33B/65B | 开源，可本地部署 |
| LLaMA 2 | 2023 | 7B/13B/70B | 改进指令跟随，商业可用 |

## 三、LLM工作原理

### 1. 预训练阶段

**目标**：学习语言的统计规律和知识

**训练任务**：
- **自监督学习**：无需人工标注
- **预测下一个词（Next Token Prediction）**：给定上文，预测最可能的下一个词
- **掩码语言模型（Masked Language Modeling）**：随机掩盖部分词，预测被掩盖的词

**预训练数据**：
- 互联网文本（网页、书籍、文章）
- 代码库
- 多语言数据

### 2. 微调阶段

**目标**：将通用知识适配到特定任务

**微调方法**：

#### 方法一：全参数微调

- 更新模型所有参数
- 需要大量计算资源和数据
- 效果最好，但成本高

#### 方法二：参数高效微调（PEFT）

| 方法 | 说明 | 优点 |
|------|------|------|
| LoRA（Low-Rank Adaptation） | 冻结主干模型，仅训练低秩矩阵 | 高效，内存占用小 |
| Adapter | 在Transformer层间插入小网络 | 灵活，可组合多个Adapter |
| Prefix Tuning | 优化输入前缀 | 参数少，效果好 |

#### 方法三：提示工程（Prompt Engineering）

- 不修改模型参数
- 通过精心设计提示词引导模型输出
- 零样本或少量样本即可使用

### 3. 推理阶段

**自回归生成**：
```
输入提示 → 模型预测第一个词 → 将第一个词加入输入 → 预测第二个词 → ... → 直到结束符
```

**解码策略**：

| 策略 | 说明 | 适用场景 |
|------|------|----------|
| Greedy Search | 每次选择概率最高的词 | 快速，但可能生成单调文本 |
| Beam Search | 保留多个候选路径 | 生成质量高，但计算量大 |
| Top-K Sampling | 从概率最高的K个词中随机选择 | 增加多样性 |
| Nucleus Sampling（Top-P） | 从累计概率达到P的词中随机选择 | 平衡多样性和质量 |

## 四、LLM能力边界

### 1. 强能力

| 能力 | 示例 |
|------|------|
| 文本理解 | 阅读理解、情感分析 |
| 文本生成 | 文章写作、代码生成 |
| 推理 | 数学问题、逻辑推理 |
| 多语言 | 翻译、跨语言理解 |
| 对话 | 聊天机器人、问答 |

### 2. 局限性

| 局限 | 说明 |
|------|------|
| 幻觉（Hallucination） | 生成看似合理但错误的信息 |
| 时效性 | 训练数据截止到某个时间点 |
| 上下文长度 | 有限的上下文窗口 |
| 数学能力 | 复杂计算可能出错 |
| 事实性 | 可能编造事实 |

### 3. 减少幻觉的方法

- 提供参考文档（RAG技术）
- 使用思维链（Chain of Thought）
- 验证输出结果
- 限定输出格式

## 五、RAG（检索增强生成）

### 1. 核心思想

将外部知识检索与LLM生成相结合，解决幻觉和时效性问题。

### 2. RAG流程

```
用户提问 → 检索相关文档 → 将文档和问题一起输入LLM → 生成答案
```

### 3. RAG架构

```
文档库 → 向量化（Embedding） → 向量数据库 → 检索 → Prompt构建 → LLM生成
```

### 4. RAG组件

| 组件 | 说明 |
|------|------|
| 文档库 | 存储领域知识文档 |
| Embedding模型 | 将文本转化为向量 |
| 向量数据库 | 存储和检索向量 |
| 检索器 | 根据问题检索相关文档 |
| 重排序器 | 对检索结果排序 |

### 5. RAG vs 微调

| 维度 | RAG | 微调 |
|------|-----|------|
| 更新知识 | 简单（更新文档库） | 复杂（重新训练） |
| 知识规模 | 无限制 | 受模型容量限制 |
| 推理能力 | 依赖LLM基础能力 | 可通过微调增强 |
| 实现成本 | 低 | 高 |

## 六、提示工程（Prompt Engineering）

### 1. 什么是提示工程

通过设计有效的提示词，引导LLM生成期望的输出。

### 2. 提示词设计原则

| 原则 | 说明 |
|------|------|
| 清晰明确 | 明确告诉模型要做什么 |
| 提供上下文 | 给出必要的背景信息 |
| 使用示例 | 提供少量示例（few-shot） |
| 指定格式 | 定义输出格式（JSON、列表等） |
| 逐步思考 | 引导模型分步推理 |

### 3. 常用提示技术

#### 技术一：思维链（Chain of Thought）

**示例**：
```
Q: 一个篮子里有5个苹果，拿走2个，又放进去3个，现在有几个苹果？
A: 第一步：5-2=3；第二步：3+3=6；答案：6
```

#### 技术二：自我一致性（Self-Consistency）

- 生成多个推理路径
- 选择出现次数最多的答案

#### 技术三：分解问题（Decomposition）

- 将复杂问题分解为多个子问题
- 逐步解决每个子问题

### 4. 提示词模板

```
你是一个{角色}。
请根据以下背景信息回答问题：
{背景信息}

问题：{用户问题}

请按照以下格式输出：
{输出格式要求}
```

## 七、LLM产品架构

### 1. 典型架构

```
用户接口 → 提示词构建 → LLM调用 → 结果后处理 → 用户反馈收集
```

### 2. 关键组件

| 组件 | 说明 |
|------|------|
| 用户接口 | Web界面、API、SDK |
| 提示词管理 | 版本控制、A/B测试 |
| LLM调用层 | 调用第三方API或自建模型 |
| 结果后处理 | 格式转换、内容过滤 |
| 反馈收集 | 用户评价、纠错机制 |

### 3. 成本考量

| 成本项 | 说明 |
|--------|------|
| API调用费用 | 按token计费 |
| 模型训练成本 | 算力资源消耗 |
| 推理成本 | GPU资源消耗 |
| 数据存储成本 | 向量数据库存储 |

## 八、产品经理必备知识

### 1. 模型选择决策

| 维度 | 考虑因素 |
|------|----------|
| 成本 | API调用vs自建模型 |
| 性能 | 模型能力是否满足需求 |
| 隐私 | 是否需要数据本地化 |
| 定制化 | 是否需要领域微调 |

### 2. 关键指标

| 指标 | 说明 |
|------|------|
| 响应时间 | 从提问到回答的延迟 |
| 准确率 | 回答的正确性 |
| 幻觉率 | 生成错误信息的比例 |
| 用户满意度 | 用户对回答的评价 |

### 3. 常见挑战

- **成本控制**：LLM调用成本较高
- **质量不稳定**：相同输入可能产生不同输出
- **内容安全**：生成不当内容的风险
- **知识更新**：模型知识有时效性
